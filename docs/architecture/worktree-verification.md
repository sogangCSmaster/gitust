# 작업 검증과 승인

웹의 `Verify command`에서 명령을 입력하고 `Run verification`으로 실행한다. 종료 코드·stdout·stderr·소요 시간을 확인한 뒤 서버가 `Verified`와 검증 SHA를 반환한 작업만 `Approve & Merge`할 수 있다. 원격 발행은 이후 별도의 `Publish to GitHub` 동작이다.

HTTP/MCP 실행 응답의 `checked_commit`은 이번 검증이 실행된 SHA이며 일반 편집 실행에서는 `null`이다. 웹은 이 SHA와 최신 작업 상태를 비교하고, SHA가 바뀌면 이전 출력을 현재 결과처럼 유지하지 않는다. 승인 요청은 사람이 확인한 SHA를 `expected_commit`으로 명시해야 한다. 오래된 화면에서 새로 검증된 다른 SHA를 승인하면 409로 거부한다. 기존의 본문 없는 승인 호출은 더 이상 허용하지 않는다.

## 웹에서 커밋된 변경 리뷰

Worktrees의 `Review committed changes`는 해당 작업의 커밋과 현재 병합 대상 브랜치를 Changes에서 비교한다. `Verified` 작업은 화면에 표시된 `verified_commit`을 요청하고 응답 SHA도 대조한다. 그 외 작업은 명시적인 `refs/heads/...`를 한 번 해석한다. 최초 응답에서 확정한 head/base SHA를 모든 파일 전환에 사용하고, 다른 SHA의 응답은 표시하지 않는다. 비교 중 브랜치가 이동해도 이미 열린 비교는 바뀌지 않으므로 최신 변경을 보려면 리뷰를 다시 열어야 한다.

화면에 원본 브랜치·대상 브랜치와 양쪽 전체 SHA를 표시한다. 기준은 생성 시점의 base SHA가 아니라 **리뷰를 연 시점의 병합 대상 커밋**이다. 미커밋 파일은 포함하지 않으며, 리뷰를 열었다고 검증·승인 자격을 부여하지 않는다. 생성 대상이 불명확하면 `main`으로 대체하지 않고 리뷰를 거부한다. 빈 비교, 바이너리·메타데이터 변경, 잘림과 조회 실패도 구분한다. 파일 트리의 blob 조회 역시 트리 응답의 커밋에 고정하며 트리로 이동하면 작업 리뷰 문맥을 해제한다.

공통 revision 조회에서 전체 40자리 hex는 객체로만 해석한다. 같은 이름의 브랜치·태그가 있거나 해당 객체가 없더라도 ref로 대체하지 않는다. 그런 이름의 ref를 의도한 호출은 `refs/heads/<이름>` 또는 `refs/tags/<이름>`을 명시해야 한다. `refs/...` 자체도 중첩 namespace 후보 없이 정확히 조회한다. 일반 브랜치·짧은 SHA·HEAD와 ancestry 조회는 기존 규칙을 유지한다.

## 작업 이름과 재시작

새 작업의 `prompt_summary`는 생성 시 `gitust-origin.json`에 선택적 표시 필드로 보존한다. HTTP/MCP가 받은 이름을 재시작 후에도 그대로 표시하며, 이름에서 브랜치·소유자·검증·승인 상태를 추론하지 않는다. 미병합 작업은 기존처럼 Pending으로 복구하고 재검증해야 한다. 이름이 없는 이전 기록과 reflog 마이그레이션 작업은 `recovered from disk`를 표시한다. 저장되지 않은 과거 이름을 추측해 복원하지 않는다.

이름은 최대 4,096 UTF-8바이트다. 공통 Git 생성 경로에서도 부작용 전에 검사하며, JSON escape 확장을 포함한 생성 기록 전체는 읽기·쓰기 모두 32KiB로 제한한다. 기존 파일 종류·symlink·ID·branch 검증과 변경 불가능한 생성 기록의 발행 절차는 유지한다. CLI sandbox는 명령 원문과 인수가 이름 필드에 새로 저장되지 않도록 `CLI sandbox command`라는 고정 이름을 사용하며 실제 실행 명령은 바꾸지 않는다.

새 코드는 이름 필드 없는 기존 기록을 읽는다. 새 이름 필드가 있는 기록은 알 수 없는 필드를 거부하는 이전 바이너리가 읽지 못하므로, 해당 작업을 유지한 채 구버전으로 다운그레이드하는 경로는 지원하지 않는다. 복구에는 같은 버전 또는 호환되는 최신 바이너리를 사용한다.

## 일반 실행과 승인용 검증

HTTP `POST /api/v1/swarm/worktrees/{id}/sandbox`와 MCP `gitust_sandbox_exec` 모두 `verify` 불리언을 받는다.

```json
{"command":"cargo test --offline", "verify":true}
```

- `verify` 생략 또는 `false`: 일반 샌드박스 명령이다. 작업 파일을 편집할 수 있으며, 성공해도 `Pending`이고 승인 자격은 부여하지 않는다.
- `verify: true`: 실행 전후에 관리 작업의 branch·HEAD SHA와 clean 상태를 확인한다. 종료 코드 0, 동일한 SHA, clean 상태가 모두 확인돼야 `Verified`와 `verified_commit`을 기록한다.
- tracked 변경, staged 변경, 무시되지 않은 untracked 파일은 검증을 거부한다. `.gitignore`가 제외한 빌드 산출물은 허용한다. 검증하려는 코드와 설정은 먼저 커밋해야 한다.
- `.git` 포인터는 관리 디렉터리와 역방향 포인터·common 디렉터리가 일치해야 한다. 활성 미추적 `.gitignore`로 파일을 숨기는 경우 거부하지만, 추적된 ignore 정책이 이미 제외한 빌드 디렉터리는 허용한다.
- index의 `assume-unchanged`·`skip-worktree` 설정은 변경을 숨길 수 있어 검증 시 거부한다. 해당 설정을 해제한 뒤 다시 검증해야 한다. Git 상태 검사에는 호출별 10초 제한을 적용한다.
- 승인 직전에 다시 clean 상태와 SHA를 확인하고, 병합 함수에도 예상 SHA를 전달한다. 검증 이후 커밋 또는 파일이 바뀌면 승인을 거부하고 재검증을 요구한다.
- 생성 대상과 SHA는 Git 관리 디렉터리의 `gitust-origin.json`으로 보존한다. reflog가 만료되어도 대상 브랜치를 바꾸지 않으며 승인 대상은 이 기록과 일치해야 한다. 기존 작업은 유효한 생성 reflog를 마이그레이션한다. 근거가 없으면 대상은 미확정 상태로 남고 검증·승인을 거부한다. 신뢰할 수 있는 메타데이터를 복구하거나 작업을 폐기하고 올바른 대상에서 다시 생성해야 한다.
- 새 명령, 실패·취소·시간 초과와 권한 검사를 통과한 Git push 시도는 이전 검증을 무효화한다. 원격 거부 또는 응답 유실 가능성이 있는 push 뒤에도 이전 `Verified`를 복원하지 않는다. 권한 단계에서 거부한 다른 사용자의 push는 작업 상태를 바꾸지 않는다.
- 승인 전 검증 결과는 메모리에만 있으며 재시작 후 `Pending`으로 돌아간다. 이미 성공한 승인·발행 기록은 별도 [영속 기록](outbound-sync.md)으로 복구한다.

## 실행 조건과 한계

HTTP 명령 실행은 SiteAdmin과 `serve --trusted-single-user-sandbox` 설정이 필요하다. MCP stdio는 로컬 사용자의 명령 실행 경로다. 현재 OS 샌드박스는 신뢰하는 단일 사용자용이며 다중 테넌트의 격리 경계로 제공하지 않는다. 실행 중 네트워크는 차단하므로 필요한 도구와 의존성은 미리 준비해야 한다.

수동 검증 명령의 의미는 운영자가 결정한다. 아래 필수 Checks가 없는 저장소에서는 `true` 같은 명령도 성공하므로 `Verified`가 특정 테스트 모음을 통과했다는 뜻은 아니다. 자동 Checks는 아래 명시한 관리 워크트리 트리거와 opt-in 설정에 한정된다. 검증 중 다른 프로세스가 파일을 임시 변경했다가 되돌리는 행위까지 증명하는 불변 실행 스냅샷도 아니다. 동일 호스트에서 작업을 동시에 직접 수정하지 않아야 한다.

## 저장소 필수 Checks

병합 대상 브랜치(예: `main`)의 루트에 `.gitust-checks.json`을 커밋하면 HTTP·MCP의 `verify: true`는 요청한 수동 명령 다음에 필수 명령도 실행한다.

```json
{
  "version": 1,
  "commands": ["cargo fmt --all -- --check", "cargo test --workspace --offline"]
}
```

- 실행 중인 대상 브랜치의 **커밋된 Git blob**에서 읽는다. 에이전트 브랜치나 호스트의 미커밋 설정 변경으로 필수 검사를 바꿀 수 없다. 설정 변경 자체를 승인하는 작업은 기존 대상 브랜치 정책으로 검증하고, 병합 후 다음 작업부터 새 정책을 적용한다.
- 설정이 없으면 기존 수동 검증을 유지한다. 잘못된 JSON·버전·필드, 빈 목록/명령, symlink/디렉터리, 읽기 오류는 검증을 거부한다. 파일은 최대 16KiB, 명령은 1~8개이며 각각 최대 4096바이트다.
- 각 명령은 별도 `/bin/sh -c --`와 프로세스 그룹으로 순서대로 실행한다. 요청 명령 또는 필수 명령 하나라도 실패하면 이후 명령은 실행하지 않고 `Failed`가 된다. 한 번의 실행 준비와 동시 실행 슬롯을 공유하며, 시간 제한과 stdout/stderr 각각 1MiB 상한은 전체 명령 묶음에 적용된다. 명령 내부의 오류 처리(`&&` 등)는 명령 작성자의 책임이다.
- 작업 디렉터리·HOME·TMPDIR의 파일은 같은 실행 안에서 공유하지만, 각 명령이 끝나면 그 프로세스 그룹을 정리한다. 다음 검사에 필요한 백그라운드 서버는 해당 검사 명령 안에서 시작하고 종료해야 한다.
- 실행 전후의 clean SHA와 정책 blob OID가 같아야 `Verified`다. 승인 직전에도 현재 대상 브랜치의 정책과 비교한다. 정책 추가·변경·삭제 시 이전 검증은 무효가 되며 다시 실행해야 한다. 재시작 시 검증 증거는 복구하지 않는다.
- 일반 실행(`verify: false`)은 필수 Checks를 실행하지 않고 승인 자격도 주지 않는다. 필수 검사만 실행하고 싶으면 수동 명령에 `true`를 입력한다. 응답의 `command`와 웹 결과에는 실제 전체 명령이 표시된다.
- 설정의 명령이 참조하는 테스트 스크립트는 검증 대상 체크아웃에서 실행한다. 스크립트 변경의 타당성은 사람이 리뷰해야 하며, Checks가 테스트 내용의 품질이나 불변 실행 환경을 보증하지 않는다. 운영자는 대상 브랜치 설정 변경을 신뢰할 수 있는 경로로 관리해야 한다.

CLI `triage approve`도 clean checkout과 index 숨김 플래그를 검사하고 확인한 SHA를 병합한다. 로컬 운영자의 명시적 승인 경로이며 서버의 검증 기록을 읽거나 필수 Checks를 자동 실행하지 않는다. CLI를 사용할 때는 운영자가 해당 커밋과 대상 브랜치의 필수 Checks 검증을 별도로 마쳐야 한다. 서버 승인 정책을 강제해야 하는 운영에서는 HTTP 승인 경로를 사용한다.

## 명령별 결과

HTTP sandbox 응답과 MCP `gitust_sandbox_exec` 결과의 `steps`는 요청 명령부터 필수 명령 순서로 결과를 제공한다. 실행기가 직접 관찰한 종료 상태와 시간을 기록하며 stdout/stderr의 문자열을 명령 결과로 해석하지 않는다.

```json
{
  "exit_code": 7,
  "steps": [
    {"command": "true", "required": false, "exit_code": 0, "duration_ms": 4},
    {"command": "exit 7", "required": true, "exit_code": 7, "duration_ms": 3},
    {"command": "cargo test", "required": true, "exit_code": null, "duration_ms": null}
  ]
}
```

위 시간은 응답 형식을 설명하는 예시다. 실제 응답에는 측정한 값을 사용한다. `required: false`인 첫 항목은 사용자가 요청한 명령이며 나머지는 대상 브랜치 정책의 필수 검사다. 종료 코드와 시간이 모두 `null`이면 앞선 실패로 실행하지 않은 명령이다. 0은 성공, 다른 종료 코드는 실패다. 전체 종료 코드는 처음 실패한 명령의 코드이며, 모두 성공하면 0이다.

웹 결과 창에서 각 명령의 Passed/Failed/Skipped와 필수 여부를 확인할 수 있다. 전체 출력은 기존 `stdout`/`stderr`에 합쳐서 표시한다. 순서·타입·전체 종료 코드가 모순된 명령별 응답은 성공으로 표시하지 않고 서버 상태 재확인을 요구한다. `steps`가 없는 이전 서버 응답도 전체 결과로 볼 수 있다.

실행한 각 단계에는 `output: {"stdout": "...", "stderr": "...", "truncated": false}`도 제공한다. 웹의 `Command output`을 펼쳐 해당 명령의 출력만 확인한다. 건너뛴 단계에는 출력이 없으며, 이 필드가 없는 이전 서버·이력에는 전체 출력만 표시한다. 각 단계는 기존 전체 stdout/stderr 각각 1MiB의 남은 캡처 예산을 공유하고, 상한 이후에도 파이프를 계속 비워 명령을 중단시키지 않는다. 따라서 앞선 명령이 예산을 소진하면 뒤 명령의 출력은 비어 있거나 잘릴 수 있다. 단계별 출력은 해당 명령의 바이트를 UTF-8로 변환하며, 서로 다른 명령이 하나의 문자를 나누어 쓴 경우 전체 출력과 다르게 대체 문자가 표시될 수 있다. 종료 상태는 출력 내용으로 추론하지 않는다.

시간 초과·실행 준비 오류·취소는 기존 오류 경로를 유지하며 완성된 `steps` 응답을 반환하지 않는다. 정상적인 완료 응답(종료 코드가 0이 아닌 실행도 포함)은 아래의 제한된 이력에 보관한다.

### 관리 워크트리 자동 Checks

대상 브랜치에 커밋된 설정에서 `"auto_run": true`를 지정하면 서버가 수락한 MCP 커밋과 Git HTTP push 뒤 필수 Checks를 실행한다. 기본값은 false이며 기존 설정의 수동 검증 동작은 그대로 유지된다. 예:

```json
{"version":1,"auto_run":true,"commands":["cargo test"]}
```

신뢰 단일 사용자 실행 옵션을 켠 서버에서 활성 SiteAdmin이 자신의 관리 워크트리를 갱신해야 한다. 로컬 MCP stdio 운영자는 기존 명시적 커밋 경로와 같이 복구된 작업도 대상으로 삼을 수 있다. Developer나 다른 소유자의 push는 자동 명령 실행 권한을 만들지 않는다. 실행 직전 활성 계정·저장소 권한·소유권, clean SHA와 커밋된 정책을 다시 확인한다. Git HTTP의 200 응답만으로 성공을 추정하지 않고 실제 ref가 요청된 새 SHA인지 확인한다.

대기열은 프로세스 메모리 안에서 최대 1024개 작업으로 제한되며 작업별 최신 대기 변경을 합친다. 실행·커밋·승인·폐기는 기존 작업 잠금으로 직렬화한다. 잠금을 기다리는 동안 새 커밋으로 대체된 실행은 건너뛰고, 수동 검증 결과나 종료 상태를 뒤늦은 자동 실행으로 덮어쓰지 않는다. 종료 시 대기 작업과 진행 중인 자동 실행을 취소하며 재시작 후 자동 재시도하지 않는다. durable 대기열·시작/시간 초과/취소 이력·명시적 재실행 UI는 후속 작업이다. 파일시스템에서 직접 실행한 Git 커밋, 일반 브랜치 변경, mirror 동기화는 트리거하지 않는다.

자동 실행은 기존 명령 단계 형식을 유지하기 위해 첫 준비 명령 `true` 뒤에 필수 Checks를 실행한다. 완료된 이력에는 `automatic: true`, `verification_requested: false`, 실제 확인한 SHA와 정책 blob OID를 기록한다. 성공 후 상태는 Pending이고 실패하면 Failed이며, `verified_commit`과 승인 자격은 부여하지 않는다. 웹 Run history는 Automatic checks로 구분하며 승인 전 수동 검증이 필요함을 표시한다. 자동 기록이 없는 이전 이력도 읽는다. 자동 기록이 생긴 저장소를 이 필드를 모르는 이전 바이너리로 되돌리면 이력 조회가 실패할 수 있다.

커밋은 성공했으나 검사 예약이 실패하면 MCP 응답에 실제 새 커밋과 `automatic_checks: "unavailable"`, `status: "failed"`를 함께 반환한다. 성공한 커밋을 취소한 것처럼 응답하지 않는다. Git push는 이미 수락한 Git 결과를 유지하고 작업 상태를 Failed로 바꾸며 서버 경고를 남긴다. 실행 준비·시간 초과·취소의 상세 오류는 아직 완료 이력에 저장되지 않는다.

## 완료 실행 이력

`GET /api/v1/swarm/worktrees/{id}/runs`는 활성 SiteAdmin에게 해당 저장소의 완료된 실행을 최신순으로 반환한다. 일반 실행과 명시적 검증의 HTTP/MCP 공통 경로에서 기록하므로, 프로세스 종료 코드가 0이 아니어도 결과를 보관한다. 결과와 함께 실행자 ID, 기록 시각, 검증 요청 여부, 검증 전후에 확인한 커밋과 필수 Checks 정책 blob OID를 저장한다. API 응답은 `Cache-Control: no-store`다.

이력은 일반 파일로 `<common Git directory>/gitust-check-runs/<worktree UUID>.json`에 저장한다. 작업별 최근 5건, 파일당 3MiB를 상한으로 두고, 명령 표시와 각 단계 명령은 4096바이트, stdout/stderr는 각각 16KiB까지 UTF-8 경계에서 잘라 보관한다. 이력용으로 추가로 잘랐으면 `history_truncated: true`이며 원래 실행 응답과 `output_truncated` 의미는 바꾸지 않는다. 잘린 명령은 재실행 입력으로 사용하면 안 된다. 명령과 출력에는 저장소 내용이 포함될 수 있으므로 이 디렉터리는 Unix에서 0700, 새 파일은 0600으로 만들고 샌드박스에서는 숨긴다.

단계별 stdout/stderr는 각각 1KiB까지 보관하며, 추가 잘림은 같은 `history_truncated`로 알린다. 단계의 `output.truncated`는 실제 실행 캡처의 잘림만 의미한다. 이 제한은 최대 9단계·5건과 JSON 이스케이프 확장을 고려해 기존 3MiB 파일 상한 안에 유지한다. 단계별 출력이 없는 기존 버전 1 이력도 그대로 읽는다.

파일은 버전·작업 ID·브랜치·결과의 작업 ID와 크기를 검사하며 symlink나 일반 파일이 아닌 입력은 거부한다. 임시 파일 fsync, atomic rename, 디렉터리 fsync 순서로 기록하고, 작업별 한 개의 staging 파일만 사용해 중단된 쓰기 잔여물을 제한한다. 같은 작업의 실행·삭제 잠금은 기록이 끝날 때까지 유지한다. 손상된 이력을 빈 목록으로 숨기거나 덮어쓰지 않으며 저장 실패 시 새 `Verified` 상태를 발행하지 않는다. 기록은 명령 완료 후에 수행하므로 저장 오류 응답이라도 명령은 이미 실행됐을 수 있다. 상태와 변경 내용을 확인한 후 재시도해야 한다. 작업 폐기 시 이력도 삭제한다.

작업 폐기는 같은 잠금 안에서 진단 이력을 먼저 지우고 Git checkout을 제거한다. 이력 정리가 실패하면 checkout을 유지해 운영자가 복구·재시도할 수 있게 하며, checkout만 먼저 사라져 접근할 수 없는 이력 파일이 쌓이지 않게 한다. 이후 Git 정리가 실패하면 이력은 이미 삭제됐을 수 있다. 별도 승인 기록은 이 진단 이력 정리에 포함되지 않는다.

이력은 진단 자료이며 승인 증거가 아니다. 재시작 시 작업 상태는 기존처럼 Pending으로 복구하고 `verified_commit`과 승인 자격을 이력에서 복원하지 않는다. 실제 승인·발행은 기존의 별도 durable 승인 기록만 따른다. 실행 준비·시간 초과·취소·checkout 재검증 실패처럼 완료 응답이 없는 시도와 durable 시작 기록은 아직 제공하지 않는다.

실서버에 로그인한 SiteAdmin은 Worktrees의 각 작업에서 `Run history`를 열어 최근 5건을 조회한다. 병합 완료 작업도 조회할 수 있다. 실행 시각·실행자·일반 실행/검증 구분·확인한 커밋·정책 blob OID와 명령별 Passed/Failed/Skipped, stdout/stderr를 표시한다. `Refresh history`로 다시 읽으며, 로딩·빈 목록·조회 실패를 구분하고 오류나 새 조회 시 이전 기록을 비운다. API 응답의 ID·개수·타입·크기·명령별 종료 상태 일관성을 검사하고, 계정 변경·창 닫기·뒤늦은 응답은 표시하지 않는다. 이력을 브라우저 저장소에 캐시하지 않는다.

이력 창은 현재 작업 상태와 분리된 읽기 전용 화면이다. 과거 성공 기록을 선택해도 현재 작업의 검증·승인 상태를 바꾸지 않으며 승인·재실행 동작을 제공하지 않는다. 잘린 명령은 진단 표시로만 사용한다. 현재 세션의 실행 결과 창은 기존처럼 별도로 유지한다.

## 회귀 검증

`tests_verification.rs`는 검증 후 새 커밋, 검증 명령의 파일 변경, 실행 전 untracked 파일, 실패한 재실행, 승인 직전 dirty 상태, 재시작 후 검증 무효화, index 숨김 설정을 검사한다. 최초 두 사례와 index 설정 사례는 수정 전 성공 응답으로 실패했고 수정 후 거부된다. 일반 MCP 편집 명령과 실제 HTTP Git push의 상태 전이도 서버 테스트에 포함한다.

`tests_checks.rs`와 `tests_required_checks.rs`는 설정의 크기·형식·종류 제한, 에이전트 설정으로의 대체 거부, 필수 명령 실패/정상 승인, 실행 중과 승인 전 정책 변경, 시간 초과 후 증거 초기화를 검사한다. 수동 `exit 0` 요청에도 대상 브랜치의 실패하는 필수 검사를 적용하는 회귀 테스트는 구현 전 실패하고 구현 후 통과했다. 웹 테스트는 실제 실행 명령과 재실행용 사용자 입력을 별도로 보존하는지 확인한다.


## 소유권과 실행 후 인증

HTTP/MCP에서 생성한 작업의 소유권은 common Git directory의 `gitust-owners/<UUID>.json`에 작업 ID·브랜치와 함께 저장하고 재시작 때 검증하여 읽는다. 이전 버전이나 CLI가 만든 소유권 기록 없는 작업은 관리자 관리 대상으로 남는다. 새로 생성하는 작업부터 소유권이 보존된다.

병합 완료 작업은 사용자별 활성 작업 할당량에서 제외한다. Developer와 MCP 경로는 계정 role과 관계없이 병합 완료 작업을 폐기할 수 없다. 일반 HTTP의 Maintainer/SiteAdmin 또는 로컬 CLI의 명시적 폐기는 체크아웃과 승인 기록을 제거하므로 발행이 필요하면 먼저 완료해야 한다. 미병합 작업은 기존 소유자 MCP 폐기를 유지한다.

실행 후 Git 상태 검사까지 끝난 시점에 계정 활성 상태와 저장소 권한을 재확인한다. 실행 도중 비활성화되면 승인용 검증 증거를 남기지 않는다. 실제 인증 DB 경로와 잠금 파일은 샌드박스에서 숨긴다.


`tests_steps.rs`와 `tests_check_steps.rs`는 명령별 결과의 출처, 실패 뒤 실행 생략, 일반 실행의 승인 자격 미부여, 전체 시간·출력 상한, 공유 파일과 명령 간 프로세스 정리, UTF-8 출력 결합을 확인한다. 외부 취소로 pipe drain이 중단되어도 reader task가 남지 않는 회귀도 포함한다.
